หลักฐานปัญหาเพิ่มเครื่อง: log วันที่ 25 กันยายน เวลา 08:09–08:11 น. มี
`PermissionError: Shared Slot requires reviewed setup and meter baseline`
จาก `PeerMembership.current_scope()` ก่อนเริ่มอ่านใน `BackgroundPolling._poll_device()`.
ตรวจฐานข้อมูลแบบอ่านอย่างเดียวแล้วพบเครื่องเปิดใช้ครบสาม Slot แต่ `slot_meter_heads`
และ `web_observations` มีเฉพาะ Slot 1–2 (ในฐานข้อมูลใช้หมายเลข 0–1).
นี่เป็นการขาดขั้นตอนสร้างฐานเมื่อเพิ่มเครื่องใหม่ ยังไม่ใช่หลักฐานว่ารหัสผ่านหรือ TLS ผิด.

การแก้ที่นำเข้า source แล้ว: ให้ขั้นตอนเพิ่มเครื่องใหม่เก็บผลอ่าน Web ที่ตรวจสอบตัวตนและ
Counter แล้ว พร้อมสร้างฐานมิเตอร์เริ่มต้นก่อนเข้าเส้นทางอ่านแบบแชร์ ไม่ข้ามการตรวจสิทธิ์
และไม่รีเซ็ตฐาน/ประวัติของเครื่องเดิม. เกณฑ์รับงาน: เพิ่ม Slot ใหม่แล้วอ่าน Counter ได้,
อ่านครั้งถัดไปผ่านระบบแชร์ได้, ผลอ่านไม่สำเร็จไม่สร้างฐานเทียม, ยอดเดิมไม่เปลี่ยน และ
กรณีเปลี่ยนเครื่องใน Slot เดิมยังต้องผ่านขั้นตอนตรวจความต่อเนื่องของมิเตอร์.

### เงื่อนไขอัปเกรดสำหรับขั้นมิเตอร์เริ่มต้น — 25 กันยายน 2569

- การไม่มี `slot_meter_heads` หรือ metadata แบบใหม่เพียงอย่างเดียว **ไม่ใช่หลักฐานว่าเป็นเครื่องใหม่**.
- ติดตั้งทับรุ่นเก่า เช่น 5.2.4 ต้องเปิดรายงานเก่าได้โดยไม่บังคับเริ่ม Wizard ใหม่
  และรักษาฐานมิเตอร์ ประวัติ ราคา และยอดบัญชีเดิม ไม่สร้างค่าศูนย์แทนรายละเอียดที่รุ่นเก่าไม่เคยเก็บ.
- เพิ่มเส้นทางรองรับเครื่องเดิมหลังอัปเกรด เพื่อให้อ่านข้อมูลใหม่ต่อได้โดยไม่ติด
  `Shared Slot requires reviewed setup and meter baseline`; ห้ามแก้ด้วยการข้ามสิทธิ์ของระบบแชร์.
- ขั้นยืนยันฐานใหม่ใช้เฉพาะการติดตั้งใหม่/เพิ่มเครื่อง/เปลี่ยนตัวเครื่องจริง ไม่ใช้กับ
  การอัปเกรดโปรแกรมหรือแก้ราคา/IP ของเครื่องเดิม และต้องไม่เปลี่ยนฐานเครื่องอื่นใน Slot 1–3.
- เกณฑ์ทดสอบก่อนรวม: ฐานจาก 5.2.4 ที่ไม่มี epoch ใหม่, ประวัติที่ไม่มี Counter รายละเอียดครบ,
  เปิดซ้ำหลัง migrate, อ่านครั้งแรกหลังอัปเกรด, และเพิ่ม Slot ใหม่หลังอัปเกรด;
  ตรวจว่าประวัติ/ยอดเดิมคงเดิม และไม่ถูกนำไปคิดเป็นยอดใช้งานใหม่.

ผลตรวจ source ครั้งนี้: การเปิด workspace ตรวจเพียงข้อมูลองค์กรและเครื่องเดิม ไม่ตรวจ epoch.
Migration 27 สร้างตาราง epoch แต่ไม่ย้ายฐานเดิมอัตโนมัติ; initializer ปัจจุบันเรียกเฉพาะ
ตอนเตรียมต้นทางเข้าระบบ LAN และอาจปฏิเสธประวัติรุ่นเก่าที่ไม่มีหลักฐาน Web ตามรูปแบบใหม่.
ชุดทดสอบ `test_app_setup.py`, `test_migrations.py`, `test_initial_slot_baselines.py`
ผ่าน 22 cases บนฐานจำลองแยก แต่ยังไม่ใช่หลักฐานว่าตัวติดตั้งทับ 5.2.4 และอ่านต่อผ่านครบ.
หลักฐานซ้อมย้ายข้อมูล 5.2.4 จาก source ก่อนหน้านี้อยู่ใน
`SUBJECT_NAME_PRESERVATION_2026_09_25.md`; ยังต้องทดสอบเส้นทาง Wizard/อ่านต่อข้างต้น.

**ผลตรวจต่อและทดสอบจริงจาก source:** การอัปเกรดปกติจาก 5.2.4 ไม่สร้างกลุ่ม LAN
อัตโนมัติ; `PeerNetworkRuntime._prepare()` คืนค่าโดยไม่ผูก shared read เมื่อยังไม่มี
`lan_peer_group`. ดังนั้นข้อกังวลเรื่อง epoch ข้างต้นไม่บล็อก standalone upgrade.
ซ้อมด้วยโค้ด release `aa8bda3` สร้างข้อมูลจำลอง แล้ว migrate schema 19 → 34:
ข้อมูลเดิม 21 ตารางคงเดิม, เปิดซ้ำผ่าน, ไม่ย้อนเข้า Wizard, อ่านต่อครบสาม Slot ได้.

## วิธีทำงานและตรวจรับ

1. เปิด issue รวม เลือกงาน P1 ก่อน สั่งงานด้วยหมายเลข เช่น “ทำ #30 แล้วตรวจตามเกณฑ์ใน issue”
2. อ่าน “ปัญหาและผลที่พบ”, “หลังแก้จะทำงานอย่างไร” และ “ผู้ใช้จะใช้งานอย่างไร” เพื่อยืนยันขอบเขต
3. ผู้ทำระบุว่ากำลังทำ/ติดอะไรใน issue และเชื่อม commit/PR; ไม่ถือว่าการเปิด PR แปลว่าตรวจผ่าน
4. รัน checklist ใน “ตรวจสอบอย่างไร / เกณฑ์รับงาน” พร้อมแนบผลก่อน–หลัง
   UX ใช้ภาพ/ภาษา/ขนาดจริง/keyboard/empty-error states; Performance ใช้ fixture เดิม,
   UI responsiveness, เวลาโหลด, RAM และความถูกต้องของยอด/ไฟล์
5. ผู้ตรวจทดลอง flow ใน source ที่ตรง commit ตรวจหลักฐานและข้อจำกัดที่ยังไม่ได้ทดสอบ
   หากไม่ผ่านให้บันทึกขั้นตอนและผลจริงใน issue เดิม
6. ปิดงานย่อยเมื่อแก้และตรวจรับผ่าน พร้อมลิงก์หลักฐาน แล้วอัปเดตรายการในงานรวม
   Closed ไม่ได้หมายถึงอนุมัติ build/release

ยังไม่มี automation/การมอบหมายผู้อื่นอัตโนมัติหรือ GitHub Project เพิ่มขึ้น
P1/P2 อยู่ในชื่อและเนื้อหาเพื่อเรียงความสำคัญ ไม่ได้เพิ่ม label หรือ milestone ใหม่
