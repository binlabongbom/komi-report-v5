# Peer transport และงานรับ/ส่งใน source 5.2.12

วันที่ 18 กันยายน 2569 — พัฒนาบน local main, ไม่ build, ไม่เปลี่ยน Host

## สิ่งที่ต่อเข้าด้วยกันแล้ว

`PeerHTTPSClient` และ `PeerHTTPSServer` ใช้ mutual TLS, ตรวจ CA/hostname และ
certificate fingerprint กับ callback ยืนยันสมาชิกที่ต้องส่งเข้ามาอย่างชัดเจน
ไม่มีค่าเริ่มต้นที่ยอมรับทุกคน ไม่สร้าง CA หรือออกใบรับรองให้เครื่องลูกค้าจากข้อมูล Broadcast
ไม่มี HTTP fallback, redirect หรือ retry คำสั่งเขียนภายใน transport
จำกัดขนาดข้อความ จำนวน worker และ timeout; เปิดพอร์ตเฉพาะเมื่อสร้าง server โดยชัดแจ้ง

`PeerDataEndpoint` ต่อการรับส่งกับ service ที่ตรวจบริษัท/Slot/ฐาน/หลักฐานอีกชั้นหนึ่ง:

- manifest/page และ dependency ของ Slot สำหรับเติมประวัติ
- คิวส่งผล Web ที่บันทึกแล้ว พร้อม ACK หลัง commit
- ประวัติตั้งค่าแบบแบ่งหน้า พร้อมตรวจจุดรับเดิมเมื่อปลายทางกู้ฐานเก่า
- งานจองผู้อ่าน สถานะ SNMP/Web เฉพาะงาน คำขออ่านร่วม และรับผล Web ของงานนั้น
- ฉบับแก้ไขการแบ่งยอด Web พร้อมตรวจบัญชีและหลักฐานในฐานของผู้รับ

`PeerSyncSession` ใช้กับ `PeerHistoryRuntime` ที่ Desktop/Agent มีอยู่แล้ว
ทำงานหลัง startup, reconnect หรือ commit ของการตั้งค่า/ผลอ่าน/ฉบับแก้ไข
จังหวะส่งเริ่มหลัง transaction สำเร็จเท่านั้น คิวในฐานข้อมูลเป็นตัวกู้ต่อเมื่อไฟดับ
ไม่มี timer ถามการตั้งค่าทุก 5 นาที ไม่มี worker ส่งข้อมูลเมื่อยังไม่ attach สมาชิกที่ยืนยันแล้ว
การส่งหนึ่งรอบมีขอบเขต ทำต่อเฉพาะเมื่อมีงานคืบหน้า; ความผิดพลาดคงคิวไว้
การตรวจและส่งคิวหนึ่งล้มเหลวไม่ลบคิวอื่น และไม่ถือว่าแค่ส่ง HTTP แล้วเป็น ACK

## การรับค่ามาใช้งาน

เมื่อได้รับประวัติครบ จะบันทึกสมาชิกต้นทางพร้อมรายการรอตรวจใน transaction เดียวกัน
`PeerSettingsRuntime` / `PeerSettingsInbox` ตรวจสิทธิ์ปัจจุบันอีกครั้งก่อนใช้ค่า
ค่าที่สืบต่อจาก head เดิมใช้ได้เมื่อไม่มีงานอ่านค้างอยู่ จากนั้นโหลดตารางอ่านใหม่
และล้าง snapshot ที่อ้างเครื่องพิมพ์เก่าใน Slot ที่เปลี่ยน
การใช้งานครั้งแรก/ประวัติคนละชุด/การแก้ชนกันต้องตรวจเลือก ไม่ใช้เวลาบนคอมตัดสินทับค่า
หน้าประวัติการตั้งค่ารองรับการยืนยันชุดบริษัท เครื่องพิมพ์ ราคา และฐาน Slot ในครั้งเดียว
ไม่คัดลอก installation ID, token หรือรหัสผ่านเครื่องพิมพ์ของคอมอื่น

ผู้ให้บริการสมาชิกที่ยืนยันแล้วต้อง bind `polling.bind_verified_settings(...)`
และ attach `PeerSyncSession` รวมทั้งบริการผู้อ่านร่วม ส่วน app รับสัญญาณ refresh แล้ว
ยังไม่มี production membership adapter เพราะยังไม่ได้โค้ด backend ที่พิสูจน์สิทธิ์ของ Host เดิม

## ฉบับแก้ไขและฐานข้อมูลเดิม

- schema 29 เพิ่มคิวฉบับแก้ไข/ACK และ cursor ของคิวตั้งค่า โดยคงข้อมูลและ ACK เดิม
- ฉบับแก้ไขไม่ส่งเลขแถวของฐานข้อมูล ใช้ hash ของเนื้อหา ขอบเขต หลักฐาน และนโยบายราคาเดิม
- ผู้รับคำนวณเทียบจากฐานของตน หากไม่ตรงจะไม่แก้ข้อมูล การบันทึกบัญชี/receipt/คิวเป็นชุดเดียว
- เมื่อ reconnect ตรวจ ACK เก่าแบบจำกัดชุด เพื่อส่งใหม่เมื่อผู้รับคืน backup ที่ไม่มีฉบับแก้ไข
- ฐาน Slot ที่ยืนยันแล้วต่อข้อมูลเปิดวันของเครื่อง/ผู้ใช้/Raw Counter โดยคงยอดก่อนหน้า
  เครื่องมือสอง 9,000 → 9,015 เพิ่ม 15; reset 120 → 5 → 15 เพิ่ม 10 หลังฐานใหม่
- ไม่เขียนทับวันที่ปิด ไม่ปลด hold โดยอัตโนมัติ ยอดผู้ใช้รวมก่อน/หลัง Archive ต้องตรงกัน
- ตรวจ Serial ที่อยู่ในสรุป Archive ด้วย เพื่อไม่สร้าง initial Slot ใหม่แล้วซ่อนตัวตนเครื่องเดิม

## หลักฐานและข้อจำกัด

ทดสอบ TLS จริงเฉพาะ loopback ด้วย CA/ใบรับรองชั่วคราวของ fixture และฐานข้อมูลแยกกัน
รวม wrong CA/hostname/member, revoke ระหว่างรับ, ขาดหลักฐาน, บันทึกล้มเหลว,
คำตอบสูญหาย, ส่งซ้ำ, restart, กู้ backup เก่า, cache rollover และยอด Archive
รายละเอียดผลชุดรวมอยู่ใน `V5_2_12_SOURCE_QA.md`

ยังไม่รับรองสมาชิกจริง, กฎ Firewall, ตัวติดตั้ง, Proxmox VM105 หรือ printer จริง
ยังไม่ใช่ช่องส่งฉบับแก้ไขราคา/เงินด้วยมือ/รายละเอียดผู้ใช้และ Raw Archive ทุกประเภท
ผล local source ไม่ใช้แทนหลักฐานว่าฟีเจอร์ทั้งแผนพร้อม build แล้ว

รายการ Host ที่ต้องอ่านเท่านั้น: `register-api.php` และ includes, ตัวจัดการ KOMI
ใน `api.php` และ schema/สัญญาที่ผูกบริษัท–installation–key–Slot
ไฟล์ `screens-license.js/.jsx` เป็น UI จึงยังใช้เป็นหลักฐานวิธียืนยันสมาชิกไม่ได้
การ login เว็บคงใช้ตรวจหน้าที่อนุญาตได้ แต่ไม่ใช้ session เว็บแทน peer credential
